# 추천 경험 성능 개선

## 목표

추천 품질을 복잡한 실시간 계산으로 높이기보다, 사전 검토를 통과한 장소를
빠르게 제시하고 사용자가 선택한 뒤 필요한 정보를 단계적으로 불러온다.

- 첫 추천은 승인 장소, 직선거리, 운영 가능 여부와 저장 선호만 사용한다.
- 실제 이동시간, 상세정보와 주변 장소는 해당 화면에서 필요해질 때 조회한다.
- 위치정보 동의 확인과 이용·제공사실 확인자료 기록은 성능을 이유로 생략하지
  않는다.
- 최적화 전후 결과 수, 거리 정책과 교통수단 일치 여부를 함께 회귀 검증한다.

## 측정 상태

- 변경 전 운영 릴리스: `0867987`
- 최적화 구현 커밋: `9811ada` ~ `8226373`
- 2026-10-02 현재 최적화 구현은 커밋과 빌드 검증까지 완료했으며 운영에는 아직
  배포하지 않았다.
- 따라서 아래의 요청·쿼리 수 감소는 코드 경로에서 확정된 값이고, 변경 후
  응답시간과 개선율은 운영 배포 후 같은 조건으로 다시 측정하기 전까지 확정하지
  않는다.

서버 캐시 상태에 따라 달라질 수 있으므로 절대값보다 변경 전후 추세를 본다.

## 정량적으로 줄어든 작업

### 첫 추천 화면

| 항목 | 변경 전 | 변경 후 | 정량 변화 |
| --- | ---: | ---: | ---: |
| 추천 성공 전 비핵심 페이지 선조회 | 4개 | 0개 | 초기 요청 4개 제거, 100% 감소 |
| 최초 카드 배경 이미지 요청 대상 | 최대 6장 | 최대 3장 | 최대 3장 제거, 50% 감소 |
| 위치 없는 지역 후보 적재 | 승인 후보 전체 | 최대 180곳 | 상한 없는 적재를 180곳으로 제한 |
| 위치와 지역이 모두 없는 추천 | 전체 후보 조회 후 처리 | DB 조회 전 400 응답 | 불필요한 후보 조회 1회 제거 |

비핵심 페이지는 추천 성공 3초 후에 선조회하므로 기능을 없앤 것이 아니라 첫 카드
표시와의 경쟁만 제거했다. 카드 이미지는 현재 카드와 양옆 카드만 먼저 내려받고,
사용자가 넘길 때 다음 이미지를 요청한다.

### 출발 준비

| 항목 | 변경 전 | 변경 후 | 정량 변화 |
| --- | ---: | ---: | ---: |
| 최초 경로 계산 | 3~4개 교통수단 | 선택한 1개 | 2~3개 제거, 66.7~75% 감소 |
| 최초 관광 상세·주변 장소 조회 | 2개 작업 | 0개 | 2개 제거, 100% 감소 |
| 최초 고비용 작업 합계 | 5~6개 | 1개 | 4~5개 제거, 80~83.3% 감소 |
| 카드와 출발 준비의 같은 경로 재계산 | 1회 | 캐시 적중 시 0회 | 중복 외부 경로 호출 100% 감소 |

다른 교통수단은 사용자가 해당 탭을 눌렀을 때 계산하고, 주변 장소는 최초 경로가
표시된 뒤 별도로 조회한다. 카드에서 확인한 경로는 5분 동안 공유하므로 같은 장소로
바로 출발 준비를 열면 외부 경로 호출 없이 재사용할 수 있다.

### 추천 DB 계산

| 항목 | 변경 전 | 변경 후 | 정량 변화 |
| --- | ---: | ---: | ---: |
| 후보 운영 상세 후속 조회 | 배치마다 최대 1회 | 0회 | 후속 DB 조회 100% 제거 |
| 한 후보의 `ST_Distance` 표현식 | 3회 | 1회 | 2회 제거, 66.7% 감소 |
| 자동차 2km 하한 판정 | 거리값 계산 비교 | `ST_DWithin` 공간 조건 | 공간 인덱스 사용 가능한 조건으로 변경 |

후보 운영시간·휴무일·체류시간·요금은 최초 후보 조회에 포함한다. 실제 경로를 아직
구하지 않은 추천 단계에서는 임의 이동시간을 만들지 않고 체류시간과 명시적 휴무만
검사한다.

## 변경 후 응답시간 측정표

운영 배포 뒤 각 조건을 캐시 비움 10회, 캐시 준비 10회 측정하여 아래 표를 채운다.
추천 응답의 `Server-Timing` 헤더에서 `recommendation`, `snapshot`, `total`을 각각
수집한다.

| 구간 | 조건 | 변경 전 | 변경 후 p50 | 변경 후 p95 | p50 개선율 |
| --- | --- | ---: | ---: | ---: | ---: |
| 초기 추천 | 한 시간·대중교통 | 0.341초 | 측정 전 | 측정 전 | 측정 전 |
| 초기 추천 | 한 시간·자동차 | 0.291초 | 측정 전 | 측정 전 | 측정 전 |
| 초기 추천 | 반나절·자동차 | 1.050초 | 측정 전 | 측정 전 | 측정 전 |
| 초기 추천 | 위치 없이 종로구 지정 | 0.212초 | 측정 전 | 측정 전 | 측정 전 |
| 출발 준비 | 자동차 선택·경로 캐시 없음 | 1.022초 | 측정 전 | 측정 전 | 측정 전 |
| 출발 준비 | 자동차 카드 확인 직후 | 비교값 없음 | 측정 전 | 측정 전 | - |

개선율은 `(변경 전 - 변경 후 p50) / 변경 전 × 100`으로 계산한다. 단일 측정값과
p50을 비교한다는 한계가 있으므로 이후에는 변경 전 릴리스도 동일한 반복 측정으로
보강한다.

## 구현 순서

### 1. 첫 화면 요청 정리

- [x] 위치가 없으면 시·군·구 선택을 서버에서도 필수 검증
- [x] 위치 없는 후보 조회에 상한을 적용해 전체 장소 적재 방지
- [x] 추천 성공 전 비핵심 페이지 선조회 금지
- [x] 활성 카드와 인접 카드만 이미지를 먼저 요청

완료 조건은 지역 없는 요청이 400 응답을 받고, 정상 추천 결과는 여전히 6곳을
반환하며, 첫 카드가 표시되기 전 비핵심 화면과 먼 카드 이미지 요청이 발생하지
않는 것이다.

### 2. 출발 준비 단계 분리

- [x] 추천에서 고른 교통수단을 출발 준비의 최초 선택으로 유지
- [x] 선택한 교통수단의 경로를 먼저 반환
- [x] 다른 교통수단은 탭을 선택할 때 조회
- [x] 관광 상세정보와 주변 장소가 최초 경로 표시를 막지 않도록 응답 분리
- [x] 주변 장소는 최초 경로 표시 후 별도로 조회

완료 조건은 자동차 추천에서 출발 준비를 열면 자동차 경로가 먼저 보이고,
대중교통·자전거와 주변 장소 장애가 자동차 길찾기를 막지 않는 것이다.

### 3. 추천 DB 계산 정리

- [x] 후보 조회와 실행 가능성 평가의 관광 상세정보 중복 조회 제거
- [x] 실제 경로가 없는 초기 추천에서는 체류시간과 명시적 운영상태만 판단
- [x] 같은 후보의 `ST_Distance` 계산값 재사용
- [x] 위치 없는 지역 후보도 최대 180곳 안에서 정렬

완료 조건은 추천 개수·거리 하한·다양성 회귀 테스트를 통과하면서 DB 조회 수와
추천 응답시간이 증가하지 않는 것이다.

### 4. 응답 이후 작업 분리 검토

- [x] 추천 계산·스냅샷 저장·전체 응답의 `Server-Timing` 구간 분리
- [ ] 운영 요청에서 스냅샷 저장이 응답 지연에서 차지하는 비중 측정
- [ ] 신뢰성 있는 비동기 큐를 마련한 경우에만 응답 이후 기록으로 전환

위치정보 이용 확인자료는 법적 운영기록이므로 이 단계의 비동기화 대상이 아니다.
추천 퍼널용 스냅샷도 유실 방지 수단 없이 단순한 fire-and-forget 방식으로
변경하지 않는다.

## 유지할 지연 조회

- 추천카드 이동시간: 활성 카드 한 곳만 조회
- 장소 상세정보: 카드를 뒤집거나 상세 화면을 열 때 조회
- 숙박정보: 숙박 일정인 경우에만 조회
- 장거리 추천: 교통편 연결 가능성을 판단해야 하므로 별도 성능 기준으로 관리

## 검증 항목

1. 동일 위치·답변에서 추천 6곳과 알고리즘 버전 확인
2. 자동차 추천의 모든 장소가 2km 이상인지 확인
3. 자동차 카드 이동시간 응답이 `driving`인지 확인
4. 위치 없는 요청은 유효한 시·군·구 없이는 실행되지 않는지 확인
5. 추천, 카드 이동시간, 출발 준비의 p50·p95를 운영 지표로 분리
6. 최적화 후 장소 선택·출발 준비·길찾기 전환율이 악화되지 않는지 확인
