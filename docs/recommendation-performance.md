# 추천 경험 성능 개선

## 목표

추천 품질을 복잡한 실시간 계산으로 높이기보다, 사전 검토를 통과한 장소를
빠르게 제시하고 사용자가 선택한 뒤 필요한 정보를 단계적으로 불러온다.

- 첫 추천은 승인 장소, 직선거리, 운영 가능 여부와 저장 선호만 사용한다.
- 실제 이동시간, 상세정보와 주변 장소는 해당 화면에서 필요해질 때 조회한다.
- 위치정보 동의 확인과 이용·제공사실 확인자료 기록은 성능을 이유로 생략하지
  않는다.
- 최적화 전후 결과 수, 거리 정책과 교통수단 일치 여부를 함께 회귀 검증한다.

  별도로 기록한다.

사용자가 넘길 때 다음 이미지를 요청한다.

### 출발 준비

| 항목 | 변경 전 | 변경 후 | 정량 변화 |
| --- | ---: | ---: | ---: |
| 최초 경로 계산 | 3~4개 교통수단 | 선택한 1개 | 2~3개 제거, 66.7~75% 감소 |
| 최초 관광 상세·주변 장소 조회 | 2개 작업 | 0개 | 2개 제거, 100% 감소 |
| 최초 고비용 작업 합계 | 5~6개 | 1개 | 4~5개 제거, 80~83.3% 감소 |
| 카드와 출발 준비의 같은 경로 재계산 | 1회 | 캐시 적중 시 0회 | 중복 외부 경로 호출 100% 감소 |

다른 교통수단은 사용자가 해당 탭을 눌렀을 때 계산하고, 주변 장소는 최초 경로가
표시된 뒤 별도로 조회한다. 카드에서 확인한 경로는 5분 동안 공유하므로 같은 장소로
바로 출발 준비를 열면 외부 경로 호출 없이 재사용할 수 있다.

구하지 않은 추천 단계에서는 임의 이동시간을 만들지 않고 체류시간과 명시적 휴무만
검사한다.

## 변경 후 운영 실측

2026-10-02 `1e57b06` 배포 직후 같은 종로구 지정 추천을 반복 측정했다. 추천 응답의
`Server-Timing` 헤더에서 `recommendation`, `snapshot`, `total`을 수집했다.

| 측정 경로 | 표본 | 구간 | p50 | p95 |
| --- | ---: | --- | ---: | ---: |
| `tuti.today` 비로그인 요청 | 20회 | 서버 추천 계산 | 22.3ms | 27.4ms |
| `tuti.today` 비로그인 요청 | 20회 | 브라우저 밖 전체 왕복 | 313.6ms | 451.2ms |
| NAS 내부 인증 요청 | 10회 | 서버 추천 계산 | 19.4ms | 32.5ms |
| NAS 내부 인증 요청 | 10회 | 추천 스냅샷 저장 | 67.0ms | 845.7ms |
| NAS 내부 인증 요청 | 10회 | 서버 전체 응답 | 88.2ms | 875.5ms |

비로그인 요청에는 스냅샷 저장이 없으므로 추천 계산만 측정된다. 인증 요청에서
스냅샷 저장은 전체 응답 p50의 약 76%를 차지했고, 10회 중 한 차례 큰 지연이 발생해
p95가 845.7ms까지 상승했다. 현재 추천 계산 자체는 20ms 안팎이지만 외부 왕복에서는
네트워크·Cloudflare 구간이 p50 약 291ms를 더했다.

변경 전 종로구 요청 0.212초는 단일 외부 왕복 측정이고 변경 후 값은 20회 p50이라
직접적인 개선율을 계산하지 않는다. 작업량은 확실히 감소했지만 사용자 체감시간
개선율을 확정하려면 동일 릴리스에서 같은 방식으로 지속 수집한 p50·p95가 필요하다.

### 실측 결론

1. 추천 후보 계산은 더 이상 주된 서버 병목이 아니다.
2. 인증 사용자의 다음 최적화 우선순위는 추천 스냅샷 저장이다.
3. 스냅샷을 단순 비동기 호출로 바꾸면 데이터 유실 가능성이 있으므로, DB outbox나
   신뢰성 있는 작업 큐를 마련한 뒤 응답 경로에서 분리한다.
4. 외부 왕복시간은 서버 계산시간보다 네트워크 영향이 크므로 사용자 지역별 p50과
   p95를 운영 지표로 계속 수집한다.

### 스냅샷 저장 경로 변경

2026-10-02 스냅샷 저장을 Next.js `after()`를 사용하는 응답 이후 백엔드 작업으로
분리했다.

- 추천 계산과 추천 ID 생성은 백엔드에서 계속 수행한다.
- 위치정보 이용 확인자료는 법적 운영기록이므로 응답 전에 동기 저장한다.
- 추천 결과 분석용 스냅샷만 응답을 반환한 뒤 저장한다.
- 추천 행동은 스냅샷과 외래키로 연결되지 않아 먼저 도착해도 정상 저장된다.
- 프론트엔드는 기존처럼 노출·선택·출발 같은 실제 행동 이벤트만 전송한다.

`Server-Timing`의 `snapshot_schedule`은 백그라운드 작업을 등록하는 데 걸린 시간이며,
실제 DB 저장시간을 뜻하지 않는다. 프로세스가 저장 도중 비정상 종료되면 해당 분석
스냅샷이 유실될 수 있으므로, 데이터 무손실이 필요해지는 규모에서는 DB outbox나
전용 작업 큐로 교체한다.

## 구현 순서

### 1. 첫 화면 요청 정리

- [x] 위치가 없으면 시·군·구 선택을 서버에서도 필수 검증
- [x] 위치 없는 후보 조회에 상한을 적용해 전체 장소 적재 방지
- [x] 추천 성공 전 비핵심 페이지 선조회 금지
- [x] 활성 카드와 인접 카드만 이미지를 먼저 요청

완료 조건은 지역 없는 요청이 400 응답을 받고, 정상 추천 결과는 여전히 6곳을
반환하며, 첫 카드가 표시되기 전 비핵심 화면과 먼 카드 이미지 요청이 발생하지
않는 것이다.

### 2. 출발 준비 단계 분리

- [x] 추천에서 고른 교통수단을 출발 준비의 최초 선택으로 유지
- [x] 선택한 교통수단의 경로를 먼저 반환
- [x] 다른 교통수단은 탭을 선택할 때 조회
- [x] 관광 상세정보와 주변 장소가 최초 경로 표시를 막지 않도록 응답 분리
- [x] 주변 장소는 최초 경로 표시 후 별도로 조회

완료 조건은 자동차 추천에서 출발 준비를 열면 자동차 경로가 먼저 보이고,
대중교통·자전거와 주변 장소 장애가 자동차 길찾기를 막지 않는 것이다.

### 3. 추천 DB 계산 정리

- [x] 후보 조회와 실행 가능성 평가의 관광 상세정보 중복 조회 제거
- [x] 실제 경로가 없는 초기 추천에서는 체류시간과 명시적 운영상태만 판단
- [x] 같은 후보의 `ST_Distance` 계산값 재사용
- [x] 위치 없는 지역 후보도 최대 180곳 안에서 정렬

완료 조건은 추천 개수·거리 하한·다양성 회귀 테스트를 통과하면서 DB 조회 수와
추천 응답시간이 증가하지 않는 것이다.

### 4. 응답 이후 작업 분리 검토

- [x] 추천 계산·스냅샷 저장·전체 응답의 `Server-Timing` 구간 분리
- [x] 운영 요청에서 스냅샷 저장이 응답 지연에서 차지하는 비중 측정
- [x] 분석용 스냅샷을 백엔드 응답 이후 작업으로 분리
- [ ] 무손실 보장이 필요해지면 DB outbox 또는 전용 작업 큐로 전환

위치정보 이용 확인자료는 법적 운영기록이므로 이 단계의 비동기화 대상이 아니다.
추천 퍼널용 스냅샷은 프론트 fire-and-forget 요청으로 넘기지 않고 서버 요청 생명
주기에 연결된 `after()`에서 처리한다.

## 유지할 지연 조회

- 추천카드 이동시간: 활성 카드 한 곳만 조회
- 장소 상세정보: 카드를 뒤집거나 상세 화면을 열 때 조회
- 숙박정보: 숙박 일정인 경우에만 조회
- 장거리 추천: 교통편 연결 가능성을 판단해야 하므로 별도 성능 기준으로 관리
