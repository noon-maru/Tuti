# 삭제·철회 복원 방지 운영

기준일: 2026-10-19. 로컬 구현·시험 단계. 운영 설치·초기화·파기·복구는 미실행.

담당자·최종 문서 승인자: 정연한. 연락 창구: admin@tuti.today.
목표 백업 보관기간: 30일. 실제 설치본·예약 작업·잔존 파일 검증 전에는 적용 완료로 표시하지 않는다.

## 동작

- 계정·개별 기록·기록집 삭제, 위치 전부 철회와 공개 중지 전에 NAS 전용 원장에 준비 기록을 내구성 있게 저장한다.
  DB 반영 후 완료 상태를 기록한다. 원장 장애를 성공한 삭제·철회로 표시하지 않는다.
- 사용자 ID 원문·이메일·좌표·기록 내용·사진은 넣지 않는다. 전용 키로 생성한 사용자
  검증값, 필요한 경우 대상 검증값, 요청 종류·시각·완료 여부와 무작위 요청 번호를 저장한다. 익명정보는 아니다.
- DB·객체 백업에 원장을 포함하지 않는다. DB 복원으로 원장이 과거 상태로 돌아가지
  않도록 별도 디렉터리에 둔다. 원장의 소실·키 분실은 자동 재개 불가 사유다.
- 요청별 서명과 서명된 파일 목록으로 변조·기록 누락·키 교체를 감지한다. 저장 중단이
  의심되거나 잠금이 남으면 점검 전 자동 처리를 중지한다. 잠금을 시간만 보고 강제 해제하지 않는다.
- DB 복원 전 현재 DB로 완료 사실이 확인되는 미완료 원장만 확정한다. 그 밖의 미완료
  요청은 실패·성공을 임의 추정하지 않는다. 재요청 또는 운영 확인이 필요하다.
- 복원 후 서비스 재개 직전에 삭제 계정과 위치 철회를 다시 반영한다. 원장보다 나중의
  위치 동의가 복원본에 실제 있으면 취소하지 않는다. 복원된 PDF·사진 삭제도 실패하면 재개하지 않는다.
- 개별 삭제·공개 중지도 재반영한다. 공개 중지 이후 실제로 다시 공개한 최신 선택은
  덮어쓰지 않는다. 본문 원본과 별도로 완성·보관한 기록집의 삭제는 기록집 삭제 요청으로 구분한다.
- 객체 정리는 원장의 계정·대상 검증값과 정확히 일치하는 이미지·PDF 경로만 대상으로 한다.
  DB에 참조가 없다는 이유만으로 공유 버킷 전체의 다른 자료를 삭제하지 않는다.
  새 객체 백업 전에도 완료된 삭제 요청의 잔존 객체를 정리한다.
- 일반 코드 롤백은 유지한다. DB 복원이 있었으면 이전 앱 이미지를 준비할 수 있지만
  개인정보 재반영과 호환성 확인을 마치기 전 서비스 시작만 보류한다.

## 설치 전 확인

1. 운영·개발 원장을 분리한다. 두 환경이 같은 원장·전용 키를 사용하지 않는다.
   2026-10-19 구성 파일상 두 환경의 객체 버킷·endpoint가 같으므로, 실제 실행 설정과
   복제 자료 범위를 확인한다. 같은 내부 사용자 ID의 개발 복제본도 개인정보 파기 범위에서 점검한다.
2. NAS 전용 경로를 준비한다. 기본 경로는
   `/var/services/homes/Tutiadmin/.tuti-secrets/privacy-ledger`이며 앱 컨테이너의
   UID/GID 1000 소유, 디렉터리 0700·파일 0600을 사용한다. 루트 작업도 파일 소유자를 유지한다.
3. 전용 32바이트 난수 키를 만들고 `PRIVACY_REPLAY_HMAC_SECRET`에 64자리 hex로 설정한다.
   키 원문을 Git·로그·문서에 저장하지 않는다. 기존 원장의 키는 임의로 교체하지 않는다.
4. Compose의 앱·ops 원장 마운트를 확인한다. 내부 경로는 `/run/tuti/privacy-ledger`다.
   Docker가 자동 생성한 root 소유 빈 폴더를 초기화 완료로 간주하지 않는다.
5. 새 서버·ops 이미지와 운영 도구를 먼저 설치한다. 원장을 쓸 수 없는 상태에서
   기능만 켜면 삭제·철회가 실패할 수 있으므로 쓰기·서명·재조회 시험을 먼저 한다.

운영 도구 설치는 변경분 검토·커밋 뒤 아래 명령으로 진행할 수 있다. 기본은 조회 전용이고,
실제 설치는 root의 명시적 실행이 필요하다. 이전 설치본은 root 전용 경로에 보관한다.

```sh
sh scripts/ops/install-legal-compliance-tools
sudo sh scripts/ops/install-legal-compliance-tools --apply
```

설치기는 새 환경변수·키 생성·DB 변경·서비스 재시작·예약 등록을 함께 실행하지 않는다.

초기화는 운영 앱을 잠시 중지하고 유지보수 잠금 아래 실제 요청이 들어오지 않는
상태에서 진행한다. `ops` 컨테이너는 `--user 1000:1000`으로 실행한다.

```sh
node_modules/.bin/tsx scripts/privacy-replay.ts --init
node_modules/.bin/tsx scripts/privacy-replay.ts --status
```

이후 `PRIVACY_REPLAY_LEDGER_ENABLED=true`를 앱·ops에 동일하게 적용한다.
원장 초기화 전의 삭제·철회 이력은 새 원장에 소급 생성되지 않는다.
원장 자체와 전용 키의 재해 복구·접근 제한도 별도로 검증한다. 같은 NAS만으로
장비 전체 손실까지 대응할 수 있다고 약속하지 않는다.

## 복원과 재개

기존 `tuti-prod-restore`의 앱 중지·확인 대기 절차를 사용한다. 원장이 활성화된 상태로
복원을 시작하면, 환경변수만 끈 뒤 재개하여 재반영을 생략할 수 없도록 대기 상태에 남긴다.

```sh
sudo -n /usr/local/sbin/tuti-prod-restore YYYYMMDD-HHMMSS --confirm-production-restore
sudo -n /usr/local/sbin/tuti-prod-restore --resume-reviewed YYYYMMDD-HHMMSS REVIEW-번호
```

두 번째 명령은 앱 중지를 다시 확인하고 현재 ops 이미지에서 재반영한 뒤 재개한다.
직접 CLI를 사용할 때는 `--backup-at=백업manifest의created_at`이 필수이며 기본은 조회 전용이다.
적용은 유지보수 잠금·앱 중지를 확인한 오프라인 경로에서만 허용한다.

수집 시작 전 또는 원장 파기 기준 전의 백업은 자동으로 완전한 재반영을 입증할 수 없다.
별도 자료로 미수집 구간을 재정리한 뒤 다음 명시적 예외를 사용할 수 있다.

```sh
sudo -n /usr/local/sbin/tuti-prod-restore --resume-reviewed YYYYMMDD-HHMMSS REVIEW-번호 --allow-legacy-ledger
```

이 예외는 과거 구간의 수동 검토 근거를 남기는 것이며 미완료 요청·무결성 오류를
무시하지 않는다. 검토하지 않은 내용을 완료로 입력하지 않는다. 원장이 삭제되거나
손상됐을 때 빈 원장으로 다시 초기화하여 우회하지 않는다.

## 30일 백업과 원장 파기

`tuti-prod-backup-prune`의 기본 실행은 조회 전용이다. 정확한 백업 ID 형식의
전용 디렉터리와 manifest 생성 시각으로 30일 초과 후보를 고른다. 수정 시각이나
파일 복사 시각으로 보관기간을 임의 연장하지 않는다. 링크·임의 경로는 파기 대상으로 쓰지 않는다.

```sh
/usr/local/sbin/tuti-prod-backup-prune
```

대상 확인 후 `--apply`를 붙이는 정기 작업을 등록한다. 이 작업은 실제 백업을
재귀 삭제하므로 보관 대상과 복구 가능 범위를 확인하기 전 실행하지 않는다.
NAS 스냅샷·복제본·다른 경로의 백업이 있다면 함께 반영한다.

전체 목록이 확인된 경우에만 같은 기준일의 완료 원장도 파기한다. 미완료 요청은
처리 확인 전 지우지 않는다. 알 수 없는 디렉터리·manifest가 있으면 원장 파기를
보류하고 점검 필요 상태를 반환한다. 정기 실행 실패·보류는 담당자가 확인한다.

기존 `tuti-prod-backup`의 성공 후 `-mtime +30` 정리는 이 작업의 설치·정기 실행을
대신하지 않는다. 실패한 백업 이후에도 보관기간 점검이 실행되도록 별도 일정을 둔다.
정기 작업 주기와 중단·실패 시 대응을 포함해 실제 파기 기한을 검증한 뒤 방침에 반영한다.

## 공고 전 시험

- 운영과 분리한 임시 DB·버킷·원장에서 삭제·철회 → 과거 백업 복원 → 재반영 시험
- 최근 위치 재동의·무관한 사용자 보존, PDF·사진 삭제 실패 때 재개 중지
- 원장 누락·키 불일치·미완료 요청·강제 종료·중복 재실행
- 복원 검토 중 예약 작업이 DB에 쓰지 않는지 확인. 개인정보 파기 도구의 새 잠금 구현도 설치한다.
- 관광 데이터 등 다른 예약 쓰기 작업은 복원 동안 일시 중지하거나 같은 잠금을 적용한다.
- 구버전 앱·코드 롤백과 현재 ops 이미지의 DB 호환성 확인

로컬 테스트는 실제 PostgreSQL·객체 저장소 복구 시험을 대신하지 않는다.
약관·권리 보호의 DB 제약은 분리된 PostgreSQL 11.11에서 별도 통과했다. 이는
운영 PostgreSQL 17과 실제 DB·버킷 전체 복원 시험의 완료를 뜻하지 않는다.

`pnpm test:legal:postgres`는 외부 접속 없이 임시 Unix 소켓과 시험 전용 DB를 만든다.
실제 마이그레이션의 제약과 `pg_dump` → 별도 DB `pg_restore` 후 제약·증빙 보존을
검증한다. 2026-10-19 로컬 결과는 7개 통과다. 운영 ORM·삭제 재반영·객체 저장소를
포함한 전체 복구 시험과는 구분한다.

CI의 `legal-postgres` 작업에는 PostgreSQL 17 검증을 추가했다. 필수 실행 파일이
없거나 서버 주 버전이 다르면 성공이나 건너뛰기로 처리하지 않고 실패한다.
GitHub 호스팅 실행기를 사용하며 운영 비밀정보·NAS 실행기는 사용하지 않는다.
아직 이 변경을 원격 실행하지 않았으므로 PostgreSQL 17 통과 결과는 미확인이다.
설치 방식은 [PostgreSQL 공식 Ubuntu 안내](https://www.postgresql.org/download/linux/ubuntu/)를 따른다.

## 위치 임시 캐시 점검

출발 경로 캐시는 기존 5분 유효기간 이후 후속 요청이 있어야 항목이 제거되는
문제를 보강했다. 이제 만료 타이머로 캐시 참조를 제거하고, 재조회에서도 만료를
검사한다. 최대 500개 제한은 유지한다. 이전 요청의 지연 실패가 새 요청을
캐시에서 지우지 않는지도 시험한다. 타이머 실행은 이벤트 루프 지연의 영향을 받으며
이 변경을 프로세스 전체 메모리의 즉시 물리적 소거로 표현하지 않는다.

이 캐시는 계정별로 분리되어 있지 않다. 전체 철회 시 여러 서버 프로세스의 캐시와
진행 중 요청을 처리하는 범위 및 파생 결과의 법적 분류는 여전히 검증해야 한다.
공공 장소 주변 결과·열차 시간표 캐시와 이용자의 출발 좌표 기반 결과도 구분한다.
이번 수정만으로 위치 철회의 전체 이행을 승인하지 않는다.
