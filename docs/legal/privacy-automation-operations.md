# 개인정보·권리 보호 자동화 운영

기준: 2026-10-29. 예약 작업은 구현·설치·활성화·실제 파기·실제 사건 통지를 구분한다.
현행 원문·시행 이력은 [법적 문서 안내](./README.md), 전체 백업·복구는 [운영 명령](../operations.md)을 따른다.
과거의 ‘공고 전’·‘로컬 구현’ 목록은 현재 활성화 지침이 아니다.

## 조회와 적용의 경계

```sh
sudo /usr/local/sbin/tuti-legal-operations-inspect
sudo /usr/local/sbin/tuti-privacy-data-maintain
sudo /usr/local/sbin/tuti-prod-backup-prune
sudo /usr/local/sbin/tuti-privacy-ledger-backup
```

앞의 세 명령은 인자 없이 상태·dry-run을 확인한다. 마지막 명령의 기본 모드는 기존
원장 복구 사본의 검증이며 새 사본 생성과 구분한다. 도구별 `--apply`는 실제 쓰기·파기이므로
대상·배포 버전·원장·보전 여부를 확인한 뒤 별도로 승인·실행한다.
원문·좌표·토큰·객체 키·사건 첨부를 일반 로그나 Slack에 출력하지 않는다.

푸시 무효 처리는 발송 당시 토큰과 ID가 일치할 때만 삭제한다. 갱신된 등록을 지우지 않는다.
전달 이력에는 문의 원문·제공자 오류 원문을 남기지 않는다. Tuti의 정리 기한을 Google·Apple의
운영·백업 자료 보유기간으로 표현하지 않는다. 복원 후 과거 푸시 등록은 초기화하고 현재 선택으로 재연결한다.

## 민감정보: 현재 입력과 기존 보호 경로

현재 마디 작성 화면은 민감정보를 받지 않으며 추가 설정·별도 선택 동의 UI를 제공하지 않는다.
일반 마디는 `sensitiveContent=false`로 보낸다. 보호 기능 플래그가 있다고 민감정보 저장을
사용자에게 안내하거나 기능을 자동 활성화하지 않는다.

서버에는 과거·기존 자료 보호를 위한 분류·열람·공개 제한·별도 동의·철회 경로가 남아 있다.
`SENSITIVE_MADI_WORKFLOW_ENABLED`와 복원 원장, 현행 별도 동의를 모두 확인하는
서버 조건을 문서 정리만으로 제거하지 않는다. 민감정보로 표시한 마디는 웹 공개할 수 없다.

철회 시 별도 원장 의무 준비 → 원문·공개 차단 → 의무 확정 → 이미지·연관 PDF·추적자료 정리
순서로 진행한다. 파일 정리가 실패하면 대기 상태로 두고 주기적으로 재시도한다.
일반 마디로 재분류해 동의 근거를 없애지 않으며, 이미 다운로드한 외부 사본은 회수하지 못한다.
기존 의무를 처리하지 못하는 구버전 ops로 복원·롤백하거나 원장을 비워 우회하지 않는다.

## 설치·예약·장애

운영 도구 설치와 타이머 활성화는 별개다. 관리자 권한으로 검토된 원본을 설치하며
실행 중인 app·ops 이미지 및 스키마의 호환성을 먼저 확인한다.

| unit | 주기 |
| --- | --- |
| `tuti-journal-rights.timer` | 직전 종료 후 1분 |
| `tuti-privacy-maintenance.timer` | 직전 종료 후 5분 |
| `tuti-backup-retention.timer` | 직전 종료 후 1시간 |
| `tuti-privacy-ledger-backup.timer` | 직전 종료 후 5분 |
| `tuti-core-backup.timer` | 매일 04:20, NAS 시간대 기준 |

원본은 `scripts/ops/systemd/`, 설치는 `install-legal-compliance-tools`와
`install-legal-compliance-timers`를 따른다. 핵심 백업은 별도 `install-core-backup`이다.
NAS systemctl은 `enable --now`를 지원하지 않으므로 enable과 start를 나누어 실행한다.
유지보수·복원 대기 잠금을 존중하고 중복 실행을 막는다. [상주 worker](../ops-workers.md)를 사용한다.

실패는 `LEGAL_RIGHTS_ALERT_WEBHOOK_URL`로 식별정보 없는 운영 알림을 보낸다.
네트워크·Docker 자체 장애에서는 발송도 실패할 수 있으므로 unit 결과와 NAS 로그를 함께 확인한다.
Slack 시험 수신은 실제 사건의 법정 통지 완료가 아니다.
