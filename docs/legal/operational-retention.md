# 문의·공유 추적·일반 오류 보관과 사건별 보전

2026-10-21 운영자가 선택한 정책의 로컬 구현이다. 운영에 배포하거나 활성화하지 않았다.
정책 선택·코드 구현은 법적 근거 승인, 실제 기한 파기 성공이나 새 방침 시행의 증거가 아니다.

## 적용 범위

| 자료 | 정리 조건 | 제외·보호 |
| --- | --- | --- |
| 문의·답변 | answered/closed이고 handledAt과 updatedAt이 모두 3년 경계 이전 또는 같은 경우 | pending/reviewing, 완료일 없는 과거 자료, 이후 수정된 자료는 삭제하지 않음. 계정 미연결 문의도 같은 조건 적용 |
| 미완료 PNG 발급 추적 | finalizedAt이 null이고 issuedAt이 30일 경계 이전 또는 같은 경우 | 완료된 발급은 제외. 완료 자료의 기존 기록·계정 삭제 연동 유지 |
| 일반 오류 | SystemLog의 diagnostic / diagnostic.error / error 조합이며 생성 후 1년 경계 이전 또는 같은 경우 | 다른 모든 범주를 제외. level=error라는 이유만으로 감사·보안·신고 이력을 지우지 않음 |

연 단위는 UTC 달력 기준이며 윤일은 이전 연도의 2월 말로 계산해 조기 파기를 막는다.
문의 완료 시각은 기존 관리자 처리의 handledAt을 사용한다. 기존 코드가 처리 때마다
handledAt을 갱신하고, 별도 계정 연결 등도 updatedAt을 갱신할 수 있으므로 보수적으로
마지막 수정일부터도 3년이 지나야 정리한다. 완료일 없는 자료에 임의 과거 시각을 채우지 않는다.
완료일 누락 자료의 개별 판정·정리는 별도이며 무기한 보존 승인이 아니다.

## 일반 오류 최소 수집

`writeDiagnosticLogSafely`는 유한 목록의 오류 코드·기능 범주, 검증한 릴리스 해시,
선택적인 소요시간만 저장한다. DB의 생성 시각·임의 로그 ID가 함께 생성된다.
자유 오류 메시지·stack·URL·본문·계정/기록 ID·토큰·정밀 좌표를 받지 않는다.
일반 `writeSystemLog`에 diagnostic 범주를 넘겨도 같은 최소화 검증을 적용한다.

추천 API의 예기치 않은 오류와 기록집 목록·완성·정리 실패에 연결했다. 이 경로의
console 출력에서도 예외 원문을 제거했다. 전체 앱의 console·컨테이너·NAS·Cloudflare
로그 수집/보관 설정을 모두 바꾼 것은 아니며, 과거 로그를 새 범주로 일괄 재분류하지 않는다.
활성화 전에는 이 도우미가 새 진단 이력을 저장하지 않는다.

## 기본 조회와 활성화 경계

DB 설정이 주어진 관리자 전용 실행 환경에서:

```sh
pnpm legal:retention:inspect
```

실제 내용·계정·대상 식별값 없이 대상 건수·기준 시각·보전/검토 필요 건수만 출력한다.
`--apply`도 `PRIVACY_EXTENDED_RETENTION_ENABLED=true`가 아니면 `mode=disabled`로
조회만 한다. 운영 환경변수는 변경하지 않았고 예제 기본값은 false다.
배포 후 조회 결과·보전 목록·정책 적용 범위와 파기 승인을 확인한 뒤 별도로 활성화해야 한다.

기존 `tuti-privacy-data-maintain`이 신규 작업을 호출한다. 기존 예약 정의는 이전 실행 종료 후
약 5분마다 점검하며, 실제 설치·배포 상태는 운영에서 별도 확인한다. 새 타이머는 만들지 않는다.
기존 복원 검토·유지보수 잠금과 실패 시 Slack 고정 문구 알림을 재사용한다.
`--restore` 모드의 기존 푸시 초기화·민감정보 철회 작업은 유지한다.

## 사건별 최소 자료 보전

보전 목록은 AppSetting의 `privacy.retention-holds.v1`에 관리 메타데이터만 저장한다.
자료 본문·이미지를 복제하지 않고, 위 세 범주의 특정 행만 기한 정리에서 제외한다.
전체 계정·기록·위치·감사·신고 자료를 포괄 보전하거나 기존 삭제·철회를 막지 않는다.
다른 범주의 실제 사건 자료는 해당 절차와 근거를 개별 검토해야 하며 이 도구가 대신하지 않는다.

등록 입력 예시(실제 개인 정보·원문을 넣지 않는 관리자 전용 JSON 파일):

```json
{
  "id": "hold-example-1",
  "resource": "inquiry",
  "targetId": "대상-행의-식별값",
  "caseReference": "CASE-EXAMPLE-1",
  "purpose": "해당 사건의 문의 처리 경위 확인",
  "legalBasis": "담당자가 개별 확인한 구체적인 처리 근거",
  "owner": "운영 담당자",
  "terminationCondition": "해당 사건 및 필요한 권리 행사 종료"
}
```

resource는 inquiry / shareTrace / errorLog 중 하나다. 등록 시 실제 대상 존재를 확인하며,
errorLog는 전용 일반 오류만 허용한다. 파일은 저장소·공유 폴더가 아닌 제한된 관리 경로에
보관하고 필요성이 끝나면 별도로 파기한다. 등록 도구는 파일을 자동 삭제하지 않는다.
근거 문자열을 썼다는 이유만으로 적법성을 승인하지 않는다. 실제 건별 검토가 먼저다.

```sh
pnpm legal:retention:hold register /관리자-전용-경로/hold.json
pnpm legal:retention:hold review hold-example-1
pnpm legal:retention:hold release hold-example-1
```

각 명령은 기본 조회이며, 확인 후 명시적으로 `--apply`를 붙여야 목록을 변경한다.
등록과 검토의 reviewedAt은 서버 시각으로만 지정한다. review는 운영자가 실제 필요성을
재검토한 뒤 사용하며 클릭·명령 실행 자체가 법률 검토를 대신하지 않는다.
release는 보전 메타데이터를 제거할 뿐 즉시 원본을 지우지 않는다. 다음 기한 정리에서
원본이 정리 조건에 해당할 때 삭제한다. 필요성이 끝난 자료의 즉시 파기는 별도 권리 처리 경로를 따른다.

90일이 지나면 정기 작업은 `reviewRequired=true`와 비정상 종료로 운영 알림을 유도하지만,
기한이 지났다는 이유로 보전 자료를 자동 삭제하거나 검토 시각을 자동 갱신하지 않는다.
미해결 상태에서는 기존 예약 주기마다 실패 알림이 반복될 수 있으므로 실제 재검토가 필요하다.
목록의 알 수 없는 버전·손상·중복·미래 검토 시각은 신규 세 범주 정리를 모두 중단한다.
보전 등록/해제와 기한 정리는 같은 DB advisory lock을 사용해 서로 엇갈려 삭제하지 않는다.

## 검증·남은 확인

단위·모의 DB 시험으로 경계일, 완료 자료 제외, 보전 제외, 조회의 무삭제, 별도 활성화,
손상 시 중단, 90일 검토, 최소 수집과 기존 감사 범주 보존을 검증한다.
실제 운영 DB의 삭제·보전 동시 실행, 실제 예약 작업·Slack 알림, 과거 자료 적용과
복원 후 운영 재개는 이번 로컬 시험으로 완료했다고 표시하지 않는다.
DB 스키마 변경·자료 삭제·운영 환경변수 변경·공고·배포는 수행하지 않았다.
기존 계정 삭제·위치/민감정보 철회와 백업 30일 정책은 변경하지 않는다.
