**Tuti 실사용성·유용성 점검 — 2026-09-08**

현재 Tuti는 지역의 관광·문화 공간을 발견하는 데 도움이 된다. 다만 핵심 약속인 “오늘 감당할 수 있는 작은 외출을 골라준다”는 아직 안정적으로 충족하지 못한다. 시간·예산 제약 위반, 지역 변경 후 이전 결과 유지, 첫 방문의 제스처 강제 학습을 우선 수정해야 한다.

서울만 되고 대구가 안 되는 상태는 아니다. 서울과 대구 도심에서는 가까운 실제 장소가 나온다. 차이는 위치를 허용했는지, 도심인지 외곽인지, 선택한 조건을 실제로 제한하는지에 더 크게 좌우된다.

**확인 범위와 해석**

- 운영 웹 `https://tuti.today`에서 실제 버튼·드래그로 질문 → 위치 거부 → 대구 선택 → 추천 → 상세 → 기록 목록 → 출발 준비를 진행했다. 별도 에이전트가 서울 → 대구 지역 변경도 실제 UI로 재현했다. 화면 응답은 모킹하지 않았다.
- 운영 서버 `http://127.0.0.1:5050/api/recommendations`에 지역·질문 조합 50개, 좌표 지정 6개를 실행했다. 좌표는 페르소나의 가상 출발점이며 현장 GPS 측정이 아니다. 알고리즘 응답 버전은 `signal-profile-shadow-v10`이다.
- 17개 시도 전체에서 기본 추천 6개를 받았다. 50개 조건 중 일부는 연속 검사 도중 요청 제한(429)에 걸렸고, 제한 시간이 지난 뒤 간격을 두어 재조회해 모두 200 응답을 받았다. 이를 일반 사용 실패율로 계산하지 않았다.
- 지역 선택 요청 50개의 관찰 응답시간 중앙값은 약 0.57초, 최대 4.67초였다. 캐시가 섞인 서버 내부 접속 결과이므로 모바일 체감 속도나 전국 네트워크 성능으로 일반화할 수 없다.
- 개발 DB는 읽기 전용 조회로 추천 가능 장소 수·지역 밀도·혼잡도 연결을 조사했다. 운영 DB의 추천 가능 플래그까지 개발과 같다고 가정하지 않았다.
- 기존 추천 테스트 10개가 통과했다. 추가로 원본 함수와 통제된 후보를 사용해 휴무·예산·장거리 질문 반영을 점검했다. 합성 데이터 재현과 운영 발생을 아래에서 구별했다.
- 웹 Chromium 390×844 화면을 확인하고 출발 화면에서 너비 320/1440의 가로 넘침이 없음을 확인했다. Android/iOS는 공통 코드와 운영 API의 플랫폼 Origin 허용을 확인했다. 스토어 설치본·OS 권한창·지도 앱 전환은 실기기 검증하지 않았다.
- 실제 일반 사용자 모집·인터뷰·현장 방문은 하지 않았다. 아래 평가는 페르소나에 따른 과업 점검이며 만족도·재방문율을 실측한 결과가 아니다. 검토한 로컬 커밋은 `87212af`이며 배포 커밋과 동일하다고 단정하지 않는다.

**1. P1 — 지역을 바꿔도 이전 지역 추천이 남는다. 운영 웹 재현**

재현: 질문 건너뛰기 → 위치 없이 둘러보기 → 서울 선택 → 추천 → 위치 설정 → 현재 위치 사용하기 → 위치 없이 둘러보기 → 대구 선택 → 메인 복귀.

화면 라벨은 ‘대구에서 추천’이지만 갤러리피치, 명보아트홀, 와룡공원, 파리공원, 북한산 자락길, 금나래아트홀을 계속 보여준다. 추천 ID가 같고 추천 API도 서울 조건으로 한 번만 호출됐다. 상태 주입 없이 실제 UI로 확인했다.

추천 캐시가 날짜·cycle·알고리즘만 확인하며 지역·좌표를 제외하고, 저장 결과를 `initialData` 및 `staleTime: Infinity`로 재사용한다. 지역 변경은 저장된 추천을 지우지 않는다. 관련 코드: [useTutiRecommendations.ts](../src/features/tuti/hooks/useTutiRecommendations.ts), [LocationAccessProvider.tsx](../src/features/tuti/location/LocationAccessProvider.tsx), [tuti.ts](../src/store/tuti.ts).

수정 기준: 질문·지역·좌표 등 추천 입력을 캐시 정체성에 포함하고, 조건 변경 시 저장 결과도 함께 무효화한다. 새 결과가 오기 전에는 이전 카드에 새 지역 라벨을 붙이지 않는다. 같은 날 서울 → 대구 → 서울 및 새로고침 복원을 검증한다.

원시 네트워크 로그와 화면 캡처는 점검용 임시 산출물로 저장소에 포함하지 않았다.

**2. P1 — ‘잠깐’의 시간 한도를 넘는 결과를 정상 추천한다. 운영 API 재현**

모든 좌표 실험은 `movement=near`, `air=quiet`, `density=quiet`였다. 서비스 내부의 `near` 가능시간은 60분이다. 아래 거리는 출발 좌표부터의 직선거리이고, 전체시간은 서버가 계산한 왕복·최소체류·대기시간 합이다. 실제 현장 소요시간 측정치는 아니다.

|출발점|결과 6개의 직선거리 범위|실행시간 평가 가능|그중 60분 초과|평가된 전체시간 범위|
|---|---:|---:|---:|---:|
|서울 시청|0.77~1.15km|6개|6개|70~97분|
|대구 동성로|0.65~0.88km|6개|6개|71~79분|
|세종 시청|1.99~13.52km|2개|2개|96~110분|
|영양읍|0.59~16.14km|5개|5개|69~136분|
|태백 시청|6.00~36.46km|3개|3개|136~289분|
|제주 시청|0.67~2.72km|5개|5개|72~110분|

예: 태백 → 정선 아리랑센터는 편도 7,319초, 2회 환승, 전체 289분이다. 그런데 결과 설명은 한적함을 강조한다. 서울 한국미술관은 전체 95분·`fitsAvailableTime=false`이면서 ‘오늘 정한 이동 범위 안에서 골랐어요’라고 설명한다.

후보 조회에 최대 반경 제한이 없고, 실행시간 초과는 제외가 아니라 점수 불이익에 그친다. 최종 6개를 채울 때 조건 위반이 남는다. 관련 코드: [service.ts](../src/server/recommendations/service.ts) 297~355행, [fatigue.ts](../src/server/recommendations/fatigue.ts) 104~126·180행 및 735행.

수정 기준: 시간 한도 초과·도착 시 휴무는 기본 결과에서 제외한다. 조건에 맞는 2곳이면 2곳을 보여주고 범위 확대를 사용자가 선택하게 한다. ‘잠깐’을 실제로 10~30분 외출로 정의할지, 60분까지 허용할지 문구와 모델을 맞춘다. 경로 미확인 결과는 검증된 근거리 결과보다 우대하지 않는다.

좌표별 응답의 핵심 수치는 위 표에 보존하고 원시 응답은 저장소에 포함하지 않았다.

**3. P1 — 0초·0m 경로가 정상 경로로 통과한다. 운영 API 재현**

제주 시청 좌표에서 제주특별자치도 민속자연사박물관은 직선 753m지만 `travelTimeSummary`가 도보 0초·0m다. 추천 1위이며 ‘실제 경로에서 … 도보 약 0m로 확인했어요’라고 설명한다.

경로 값 검증이 null만 차단하여 0을 통과시키고, `Number(null)` 또는 빈 문자열도 0으로 바뀔 수 있다. 경로 객체가 있으면 직선거리 평가를 생략하지만 실행 가능성 검사는 0초를 값 없음으로 취급하여 생략한다. 카카오 원본 응답이 0인지 null인지까지는 확인하지 않았다.

관련 코드: [kakaoMapClient.ts](../src/server/maps/kakaoMapClient.ts) 227·364행, [travelTimeSummary.ts](../src/server/departure/travelTimeSummary.ts) 7행, [executionFeasibility.ts](../src/server/recommendations/executionFeasibility.ts) 104행, [fatigue.ts](../src/server/recommendations/fatigue.ts) 123·615행.

수정 기준: 출발·도착이 떨어져 있는데 시간·거리가 0이면 경로 미확인으로 처리한다. 지도 제공자 응답 검증과 순위·설명·실행 검사에서 같은 유효성 기준을 사용한다.

**4. P1 — ‘입장료 무료’가 유료 입장을 막지 못한다. 운영 API 및 공식 안내 확인**

세종 + 잠깐 + 조용함 + 한적함 + `budget=free` 결과에 국립세종수목원이 포함됐다. 추천 응답에는 요금이 없었지만 같은 서비스의 상세 API에는 성인 5,000원과 일부 면제 대상이 명시돼 있다. 공식 이용안내도 일반 성인 개인 입장료 5,000원을 안내한다. [국립세종수목원 공식 요금안내](https://sjna.koagi.or.kr/sjna/viewngGdnc/useGdnc.jsp).

무료 전후 결과 6개와 순서가 동일했다. 요금 없음은 무료가 아니며, 일부 대상 면제는 모든 성인의 무료 입장이 아니다. 통제된 후보 실험에서도 입장료 30,000원 장소가 무료 조건의 최종 배열에 남았다.

수정 기준: 필수 입장료와 선택 체험비, 일반 요금과 면제 대상을 구분한다. 명시적 무료 선택에는 일반 입장료 0원 확인 결과를 사용하고, 요금 미확인은 별도로 알린다. 요금 데이터는 추천과 상세에서 일관되게 사용한다.

관련 코드: [AuxiliaryConditions.tsx](../src/features/tuti/components/AuxiliaryConditions.tsx), [fatigue.ts](../src/server/recommendations/fatigue.ts), [executionFeasibility.ts](../src/server/recommendations/executionFeasibility.ts).

**5. P1 — 첫 방문에 ‘눌러서 출발 준비’가 작동하지 않는다. 운영 웹 재현**

대구 첫 추천에서 활성 카드를 클릭했으나 출발 화면이 열리지 않았다. 좌우 드래그 후 상세 안내로 넘어갔고, 위 드래그로 상세, 다시 아래 드래그로 기록을 거쳐 출발 안내에 도달했다. 이후 카드 클릭으로 출발 준비가 열렸다.

첫 안내는 좌우 카드 → 위로 상세 → 아래로 기록 → 출발 순서이며, 앞선 안내 중 카드 탭을 코드가 무시한다. 건너뛰기 버튼이 없다. 키보드·보조기술의 첫 안내 완료가 어려운 점은 코드상 확인이며 별도 보조기기 실측은 하지 않았다.

수정 기준: 첫 카드 탭을 즉시 작동시키고 안내를 선택형으로 제공한다. 상세·기록·출발에는 버튼 대안을 두고 제스처를 보조 조작으로 제공한다. 관련 코드: [RecommendationsScreen.tsx](../src/features/tuti/screens/recommendations/RecommendationsScreen.tsx) 326~336·466~473·823~868행, [RecommendationsFlow.tsx](../src/features/tuti/flows/RecommendationsFlow.tsx) 478행.

사진 중심 화면은 분위기를 전달하지만, 장소명·위치·시간을 비교하려면 상세로 들어가야 하는 부담도 있다.

**6. P1/P2 — 질문을 바꿔도 목적에 맞는 결과 차이가 나지 않는다. 운영 및 함수 실험**

좌표 없이 지역만 선택했을 때 서울·대구·세종·강원 네 지역 모두 ‘잠깐 / 한두 시간 / 반나절 / 오늘 하루+내일 당일치기’의 장소 6개와 순서가 같았다. 장거리 여정도 없었다. 결과가 같다는 사실만으로 모든 질문이 무시된다고 단정할 수는 없지만, 서로 다른 시간 규모를 사용자가 체감할 결과 차이로 연결하지 못한 것은 확인됐다.

|지역|시간 규모 네 가지의 장소·순서|조용함 → 트인 곳의 기존 장소 유지|한적함 → 활기의 기존 장소 유지|
|---|---|---:|---:|
|서울|모두 동일|2/6|4/6|
|대구|모두 동일|0/6|4/6|
|세종|모두 동일|3/6|6/6, 순서도 동일|
|강원|모두 동일|4/6|5/6|

공기·밀도 질문에 따라 결과가 바뀌는 경우는 분명 있다. 그러나 서울 ‘트인 곳’ 1위는 라이브 공연장 롤링홀이었다. 같은 서비스의 상세 소개 역시 공연장으로 설명한다. 공통적인 감성 문구만으로 넓은 시야·가벼운 산책 적합성을 검증하기 어렵다.

위치가 있는 장거리 경로는 코드에서 기본 공기·밀도 답변을 후보 선정에 사용하지 않는다. 원본 장거리 함수에 외부 DB·교통 응답만 고정한 실험에서 공기 3 × 밀도 3의 9조합이 같은 장소·순서를 반환했다. 이는 운영의 실제 장거리 시간표 9회 조회 결과는 아니다. 관련 코드: [service.ts](../src/server/recommendations/service.ts) 143~191행, [longDistancePlanner.ts](../src/server/recommendations/longDistancePlanner.ts) 189~224행.

또한 ‘오늘 하루’ 이후 선택지는 내일 당일치기와 오늘 숙박뿐이다. 오늘 출발·오늘 귀가 의도를 입력하기 어렵다. 관련 코드: [intakeSteps.ts](../src/features/tuti/data/intakeSteps.ts).

수정 기준: 장거리도 답변을 후보 선정부터 반영한다. 출발지를 모르면 일정을 만들 수 없음을 알리고 수동 출발지 입력을 제공한다. 태그 검수에는 실내/실외, 탁 트인 조망, 실제 산책로, 공연 관람·예약 필요 여부를 사용한다.

**7. P2 — 위치를 거부한 사용자의 출발 단계가 막힌다. 운영 웹 재현**

지역 선택만으로 추천·상세까지는 사용할 수 있었다. 하지만 출발 준비를 펼치면 ‘현재 위치 확인하기’만 있고, 직접 출발지를 입력하거나 목적지를 지도 앱에서 여는 대안은 없었다. 관찰된 화면에는 링크가 없었다. 상세에는 주소·소개·운영시간이 있어 사용자가 다른 지도에서 직접 검색하는 것은 가능하다.

수정 기준: ‘지도에서 장소 보기’, 주소 복사, 수동 출발지 입력을 제공한다. 위치 실패의 timeout/unavailable도 지역 선택으로 복구한다. 현재 코드는 권한 denied일 때만 지역 선택을 연다. 관련 코드: [DeparturePlanScreen.tsx](../src/features/tuti/screens/departure/DeparturePlanScreen.tsx) 232행, [LocationAccessProvider.tsx](../src/features/tuti/location/LocationAccessProvider.tsx) 152~158행.

**추가로 확인한 위험과 한계**

|항목|확인 수준|실사용 영향과 조치|
|---|---|---|
|앱을 켜 둔 채 서울 → 대구 이동|코드 확인, 실제 도시 간 이동 미실측|이미 좌표가 있으면 OS 재조회 없이 반환한다. 좌표 취득 시각·유효기간과 새로고침을 도입하고 추천·출발 캐시도 좌표별로 구분해야 한다.|
|타지역 동명 장소의 혼잡도 연결|읽기 전용 개발 DB + 원본 서버 함수 재현|성남 마루공원에 서울 강남 수치 58.6을 사용한다. 성남 원천은 65.53이다. 여수 성산공원에는 김제 수치를 연결한다. 오늘 두 마루공원 등급은 모두 medium으로 화면 등급 변화까지 관찰한 것은 아니다. 시군구·장소 식별자로 연결해야 한다.|
|오늘 운영 표시|코드 확인|일부 휴무 문구를 해석하지 못해도 ‘오늘 운영’으로 표시할 수 있다. 확인·미확인을 구분하고 출발 날짜 기준으로 검증해야 한다. 실제 휴관일 헛걸음은 관찰하지 않았다.|
|입장료·주차 숨김|코드 확인|상세 항목을 앞의 3개만 보여줘 운영시간·휴일·체류시간이 있으면 비용·주차가 빠진다. 출발 결정 필수 정보는 접더라도 접근 가능하게 제공해야 한다.|
|장소 공유 링크|코드 확인 + 상세 URL이 홈 주소인 것 관찰|상세는 history.state에만 담고 공유는 현재 URL을 사용한다. 수신자에게 같은 장소를 열어 주는 place ID 링크가 필요하다. 실제 공유 발송은 하지 않았다.|

|단기 기록의 유용성|빈 기록 목록까지 실제 진입|기록 작성·사진 업로드·복귀 알림·장기간 재사용 효과는 이번 감사에서 평가하지 않았다.|

**지역·플랫폼에 관한 판단**

개발 DB 추천 가능 장소는 6,973개로 서울 656개·대구 220개·세종 13개다. 1.5km 이내 후보는 서울 시청 83개, 대구 동성로 33개, 대구 현풍 1개, 제주 시청·세종 나성동·봉화읍 각 2개였다. 관광·문화시설 중심의 데이터이므로 모든 동네의 가까운 쉼터를 균등하게 포함한 데이터는 아니다. 운영의 실제 태백·영양 결과에서도 이 한계가 드러났다.

서울 일부 장소에는 실시간 혼잡 자료가 있고 다른 지역은 관광공사 예측 또는 지역 패턴 추정이다. 대구 상세는 ‘지역 방문 패턴 예상’이라고 구분해 설명해 긍정적이다. 이를 현재 현장의 실제 인파 측정으로 해석하면 안 된다.

웹·Android·iOS Origin의 운영 API preflight는 모두 정상(204)이다. 공통 추천 서버의 시간·예산·지역 문제는 앱에서도 영향을 줄 수 있다. 네이티브 OS 동작은 직접 확인하지 않았고 로컬 앱 자산 날짜도 달라, 세 플랫폼이 동일한 사용감을 제공한다고 판정하지 않는다.

**권장 수정 순서와 완료 기준**

1. 지역·좌표 변경의 캐시 오류와 0경로 검증부터 수정한다. 잘못된 도시·잘못된 이동시간 표시가 없어야 한다.
2. 시간·휴무·무료 조건을 검증된 제한으로 적용한다. 후보 부족 시 개수를 줄이거나 조건 확대를 제안한다. 6장을 채우는 것보다 조건을 지키는 것을 우선한다.
3. 첫 카드의 상세·출발을 바로 사용할 수 있게 하고, 지역 변경·지도 열기·수동 출발지를 제공한다.
4. 장거리의 질문 반영, 실제 장소 성격 태그, 동명 장소의 지역 연결을 정비한다.
5. 이번 출발 좌표 6개와 17개 시도·질문 조합을 회귀 기준으로 사용한다. 응답 성공만 검사하지 말고 지역 일치, 시간 초과 여부, 일반 입장료, 경로 유효성을 확인한다.

수정 후에는 실제 대상 사용자 6~8명을 모집해 ‘설명 없이 3분 안에 갈 만한 곳 한 곳 결정 → 비용·운영·이동을 자기 말로 설명 → 지도 열기’를 관찰하는 것이 좋다. 서울·대구 도심, 외곽 거주자, 위치 거부 사용자, 제스처에 익숙하지 않은 사용자를 포함한다. 성공률·도움 요청·조건 위반을 기록하고 실제 방문 의사와 결정 이유를 묻는다. 이 단계가 있어야 정서적 유용성과 반복 사용 가치를 판단할 수 있다.

이번 작업에서는 서비스 동작 코드를 수정하거나 배포하지 않았다. 이 보고서와 인증정보를 제외한 재현 증거만 저장했다. 운영에서 정상 사용자 경로로 생성된 익명 세션·동의·추천·활동 로그와 상세 조회 캐시는 발생할 수 있다.
