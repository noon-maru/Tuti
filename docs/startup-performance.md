# 앱 시작·약관 확인 최적화

현행 구조: 계정별 기기 캐시 → 백그라운드 서버 검증. 아래 날짜별 수치는 당시 API 측정이며
현재 실기기 시간을 뜻하지 않는다. 필수 약관 화면·재확인 UI는 앱 영역 안에서 표시한다.

## 2026-10-23: 측정과 원인

운영 `GET /api/service-terms`를 같은 NAS에서 로그인 없이 읽기 전용으로 측정했다.
기기 저장소, 사용자 인증, 실제 Android/iOS 렌더링 시간은 포함하지 않는다.

| 측정 경로 | 3회 총 응답 시간 |
| --- | --- |
| NAS 내부 `127.0.0.1:5050` | 15.1ms / 9.0ms / 7.9ms |
| 공개 도메인·TLS·터널 | 386.2ms / 366.7ms / 305.8ms |

앞선 공개 도메인 5회 측정은 287.9~1,045.5ms였다. 내부 HTTP 응답과 외부 요청의
차이는 네트워크·DNS·TLS·프록시 등의 영향이며, DB 조회에 300ms가 걸린다는 의미는 아니다.
내부 측정 역시 DB 단독 실행 시간은 아니다.

기존 앱은 `NativeAppUpdateNotice`가 버전 확인을 완료해야
`InitialServiceTermsGate`를 마운트했다. 따라서 네이티브 앱의 버전 확인과 약관 확인은
순차 대기였다. 약관 확인에는 시행 예정 원문 조회와 이미 동의한 원문의 재전송도 포함됐다.

## 2026-10-23 최적화

- 진입 게이트의 effect와 버전 안내의 effect를 함께 마운트해 두 조회를 병렬 시작한다.
  일반 Providers·분석·추천은 두 조건을 모두 통과하기 전에는 마운트하지 않는다.
  이론상 대기 구간은 `버전 확인 + 약관 확인`에서 `max(버전 확인, 약관 확인)`으로 줄어든다.
  요청 개수 자체는 동일하며, Android/iOS에서 절약된 시간은 아직 실측하지 않았다.
- 최초 진입은 `GET /api/service-terms?scope=entry`를 사용한다.
  현재 시행 중인 약관만 확인하므로 약관 release 조회는 2회에서 1회로 감소한다.
  사용자 인증과 계정별 동의 조회는 그대로 유지한다.
- 동의 완료 계정에는 버전·원문 해시·시행일·동의 여부만 내려준다. 미동의·익명·만료
  계정은 서버 원문을 받아야만 명시적으로 동의할 수 있다. 동의를 기기 캐시로 대체하지 않는다.
- 확정 원문을 사용하는 DB 대역 회귀 시험에서 전체 응답은 **30,225 bytes**, 동의 완료
  진입 응답은 **331 bytes**로 **98.9% 감소**했다. 압축 전 UTF-8 기준이며, 운영의
  `legalPolicyRelease` 메타데이터가 포함되면 크기는 조금 달라진다. 공개망 지연이 같은
  비율로 줄어든다는 뜻은 아니다.
- 별도 `ServiceTermsNotice` 재동의 패널은 삭제한다. 사용 중 실제 428 미동의 이벤트가
  발생하면 모달을 겹치지 않고 최초 동의 화면에서 현재 약관을 확인한다.
- GET 응답에 `Server-Timing: auth;dur=..., terms;dur=...`를 추가해 배포 후 인증과
  약관 처리 시간을 외부 왕복 시간과 구분할 수 있게 했다. 토큰·이메일은 포함하지 않는다.

## 유지하는 안전장치

동의 API 응답은 `private, no-store`이며 계정 간 공유 HTTP 캐시를 쓰지 않는다. 서버 원문 무결성,
필수 연령·중요 조항 확인, 계정별 동의 영수증, 동의 후 버전·해시 재확인, 조회 실패 시
일반 이용 차단, 계정·삭제·문의 권리 경로는 유지한다. 약관 원문과 실제 법적 시행 시점은
변경하지 않는다. 일반 앱 버전 업데이트 안내도 제거하지 않는다.

## 2026-10-26 계정별 기기 캐시와 백그라운드 확인

- 서버에서 현행 약관 동의가 확인되면 기기 Preferences에 계정 ID·약관 버전·원문 해시를
  저장한다. 인증 토큰·약관 전문은 저장하지 않으며 서버 동의 영수증으로 사용하지 않는다.
- 다음 실행에서는 같은 계정의 캐시가 있으면 약관 화면을 먼저 그리지 않고 일반 화면으로
  진입한다. 기기 캐시를 읽는 짧은 대기는 남을 수 있으며 네이티브 앱 버전 확인도 별도로 유지한다.
- 현행 약관 조회는 백그라운드에서 계속 진행한다. 서버가 미동의를 확인한 경우에만 캐시를
  지우고 재동의 모달을 표시한다. 통신 실패만으로 이미 진입한 화면을 동의 화면으로 되돌리지 않는다.
- 저장값이 없는 계정은 서버 확인 후 최초 동의 화면을 사용한다. 현재 동의가 이미 있으면
  캐시를 새로 저장하고 메인으로 이동한다. 따라서 이 기능 도입 후 첫 실행은 서버 확인이 필요하다.
- 로그아웃·계정 삭제·다른 계정으로 전환 시 이전 계정 캐시를 지운다. 계정별 키로 다른 계정에
  동의를 재사용하지 않으며, 세션 변경 시 게이트도 새 계정 기준으로 다시 확인한다.
- 실제 API의 인증·동의 검사와 428 차단은 변경하지 않는다. 로컬 캐시 변조나 오래된 캐시가
  서버 권한을 부여하지 않는다. API의 실제 미동의 응답은 캐시보다 우선해 재확인을 시작한다.
- 캐시 저장 장애는 실제 서버 동의 성공을 실패로 바꾸지 않는다. 캐시 저장 큐를 인증 저장소와
  분리해 장애가 로그인 정보 조회를 막지 않게 한다.

## 배포 후 확인

웹과 네이티브 번들의 반영은 별개다. 새 빌드를 올렸다는 사실만으로 실제 설치본의 회귀 확인이 완료되지는 않는다. 배포 후 공개 API의 Server-Timing,
이미 동의한 실제 계정의 응답 크기, Android/iOS의 기존 설치 업데이트 후 첫 표시 시간을
확인해야 한다. 현재 문서의 수치를 배포 후 실기기 개선 실측으로 해석하지 않는다.
